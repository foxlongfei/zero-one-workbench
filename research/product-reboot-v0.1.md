# 两项目产品层重建 V0.1

时间：2026-09-29
状态：EXECUTING

## 总原则
用户只负责体验、操作、提出感受和要求。技术复杂性、开源检索、许可、算法、接口、证据、版本和替换方案由后台承担。

产品层验收唯一优先问题：**用户现在能不能打开、看见、操作，并在真实生活里完成一次任务？**

旧成果不删除；全部降级为 MODULE / EVIDENCE / SOURCE，只有接入整机后才重新成为产品能力。

## 产品 A｜运动达人
第一屏必须是完整人体，而不是项目状态、任务编号或局部骨骼。

V0 原型闭环：
1. 完整3D人体：旋转 / 缩放 / 点选 / 搜索。
2. 一句自然语言：今天想练什么 / 有什么条件 / 多长时间。
3. 返回一份现在可执行的训练。
4. 动作可以直接查看示范与关键提示。
5. 用户完成后反馈：容易/困难/疼痛/完成度。
6. 下一轮根据反馈调整。

底座策略：优先复用完整 Human Atlas / BodyParts3D 浏览器实现；现有右上肢OBJ、BICEPS-DYNAMIC、动作库作为插件，不再承担“造完整人体”的任务。
视频姿态：优先 Pose2Sim + MMPose/RTMPose 等成熟能力，先接后补，不自研基础识别算法。

## 产品 B｜堪舆先生
第一屏必须是一个可直接提问的“先生”，而不是 Z05 / RULE_TABLE / 研究编号。

V0 原型闭环：
1. 用户用普通话说现实问题。
2. 系统自动判断还缺什么现实输入并追问。
3. 内部选择当前真正会运行的方法。
4. 调用地图/方向/时间/历法/已有Z05等工具。
5. 返回：采用的方法、实际运行过程、结果、边界。
6. 用户可展开“为什么/来源”，默认不显示后台技术细节。

第一版允许只完整跑通少数方法；不会的明确说不会，不用假结果填空。

## 前后台边界
前台默认禁止出现：MAIN/SUB/TEMP、M01-M04、Z05-B、OBJ ID、RULE_TABLE、commit、validator、source-binding 等工程术语。
这些全部进入“开发/证据”折叠层。

## 立即停止
- 停止以补齐局部人体资产为“完整人体”路径。
- 停止为了完美证据阻止原型出现。
- 停止横向增加用户看不见的模块。
- 停止把后台节点完成当作产品完成。

## 发布节奏
先整机，再插件；先能用，再打磨。
每个有效工作周期必须让两个原型之一出现用户可见变化，否则默认低优先级。
